## 1. 实验纪律（读三遍）

这四条都是踩过的坑，违反任何一条都会得出错误结论。

### 1.1 一次只改一个变量

| 反面案例 | 后果 |
|---|---|
| 第 3 轮同时看 titleW 与路由 | 结论互相污染，两条都错 |

### 1.2 样本量不到 50 不定结论

| 案例 | 15 条时 | 扩样后 |
|---|---|---|
| titleW ×3 vs ×1.3 | ×3 更优（67% vs 60%） | 32 条打平、59 条打平 |

**15 条上 1 条题的差距 = 噪声。**

### 1.3 评测的输入必须与生产一致

第 16 轮：评测把 40 字原子碎片喂给 rerank，生产喂的是正文前 200 字。这个差异让结论反了 **17pp**。

**改评测脚本前，先读一遍生产代码怎么调用的。**

### 1.4 「空断言」是最强的断言

PrecisionMemBench 的 `shouldOnlyInclude: []` 意味着「只应返回空」。初版判分把它当成「无断言」跳过，通过率从 13.2% 虚报到 44.7%。

**空数组 / 空集合 / null 都要当成一个必须满足的条件，不是「没有条件」。**

## 2. 三刀的执行计划

### 第一刀：最近窗口保底

**假设**：2.2 的 M01/M02 低于官方 BM25 基线，是因为基线有「最近 6 轮原文」这条不依赖检索的保底通道，而 kb2 没有。

**变量**：`RECENT_WINDOW` = 0（现状） vs 6（对齐基线）

**改哪里**：适配器层（`mykb2_bridge.mjs` 的 `search` op），不改 kb2 内核。

```
返回 = 最近 N 轮原文（保底） + 检索结果（补充）
```

**对照组**：
- A：现状（只返回检索结果）
- B：最近 6 轮 + 检索结果
- C：只返回最近 6 轮（验证保底通道单独能拿多少）

**指标与样本**：
- M01 全量 + M02 全量，官方 harness
- 判定：B 相对 A 提升 ≥ 3 分（超过 ±2 分的噪声带）
- 成本：一次全量约 ¥13（网关账本实测）

**风险**：上下文变长，挤占答题模型的 token 预算；工程库不该开（N=0）

**回滚**：适配器改动一行常量，`git checkout` 即回

**验收问题**：如果 B 与 A 打平，说明「保底」不是原因，需要重新诊断——那时的下一步是查「卡粒度」（一轮一卡 vs 事实级）。

---

### 第二刀：查询向量缓存

**假设**：166 ms 的 embedding 往返里，重复查询占相当比例；缓存能省掉这部分。

**变量**：缓存关（现状） vs 开（LRU 1000 条）

**改哪里**：`src/server.mjs` 的检索入口，key = query 文本的 sha1

**对照组**：
- A：现状
- B：开缓存，**冷启动后连跑两次同一 query**

**指标**：
- 延迟：p50 / p95（第二次调用的延迟）
- 一致性：缓存命中时**检索结果的排序必须相同**
- 命中率：`memory_stats` 已暴露

**判定**：命中时延迟 ≤ 40 ms，且 top-k 排序一致

**实测修正（2026-11-20）**：同一 query 两次调用 embedding，向量并不逐字节相同——
最大差值 1.22e-3、平均 2.25e-4、余弦相似度 **0.99995668**。
这是模型服务的浮点噪声，排序不会因此改变。所以验收标准从「逐字节相同」放宽为
「排序相同」——这不是降低标准，是承认向量本身就有噪声。

**风险**：query 里含时间敏感词（「今天」「现在」）时，缓存会返回过期结果

**处理**：检测到时间词就跳过缓存；或用 5 分钟 TTL（双层保险）

**回滚**：一个环境变量 `MEM_CACHE=0` 关闭

---

### 第三刀：抽取式改写

**假设**：PrecisionMemBench 的 Alias resolution 3/23，是因为 `k8s`/`kube` 到 `kubernetes` 的映射依赖字符重叠，而二元组分词是为中文设计的。

**变量**：无改写（现状） vs 抽取式改写（关键词 + 别名表）

**只做确定性变换，不做生成**：

1. 去停用词与语气词
2. 别名表扩展：`k8s|kube` → `kubernetes`
3. **法学档位的法律术语别名**：如 `善意取得` / `善意受让` 之类，需人工维护

**对照组**：
- A：现状
- B：加别名扩展
- C：别名扩展 + 停用词剥离

**指标**：
- PrecisionMemBench 的 Alias resolution 分类（3/23 → 目标 ≥ 8/23）
- 工程库 59 条标注（不能退步：top1 保持 93.2%）

**样本量**：Alias 分类 23 条——**低于 50 条的门槛，只能当方向性信号，不能定论**

**风险**：别名表扩展过度会把无关卡片拉进来（撞 `shouldOnlyInclude`）

**处理**：别名扩展只加权重（如同义词路径），不改变原有匹配

**回滚**：别名表是独立数据文件，删掉即回

## 3. 执行顺序与理由

```
第二刀（缓存，20 行，无风险）
   ↓
第一刀（窗口保底，30 行，需要跑官方 harness）
   ↓
第三刀（改写，50 行 + 别名表，样本不足只能当信号）
```

先做缓存，因为它是纯收益、可立即验证、不影响任何已有结论。

再做窗口保底，因为它直接回应「为什么打不过基线」这个最紧的问题。

最后做改写，因为样本量不足，且别名表需要人工维护，属于长期投入。
