# 2026-11-21 重构：真源矩阵与增量索引

## 结论

两条原则落到了代码里：

1. **唯一真源** —— 路径、常量、阈值、端口各有一处定义，其余模块 import。
2. **增补而非重构** —— 索引默认走增量同步，不再每次删库重建。

实测：索引同步 964ms → 38ms（**25.4x**），向量陈旧率 14%（884 条）→ 0。

## 一、真源矩阵

### 新建

| 文件 | 职责 |
|---|---|
| `src/paths.mjs` | vault / index / db / stamp 四个路径的唯一解析入口 |
| `src/constants.mjs` | 嵌入模型名、弱匹配阈值、维度 |
| `lib/constants.js`（插件侧） | 去重阈值、蒸馏参数、web 端口、vault 兜底 |

### 顺带修掉的真实缺陷

- **`api.js` 的 `captureMinChars ?? 200` 与 schema 的 `800` 不一致**，面板显示值 ≠ 运行值。
- **`sync-index.mjs:64` `fsSync.existsSync` 把函数当对象**，必然抛错后被 catch 吞成「补抽失败，跳过」。
- **索引重建调子进程未传 `MEM_VAULT`**，索引被建到空库 `~/.memory-vault`，但「最后同步时间」写回了真 vault —— 真索引永久落后却显示已同步。

## 二、增量索引

### 设计

`build()`（全量）保留作首次建库与修复用；新增 `sync()`（增量）：

```
扫磁盘 {rel: mtime} → 读索引 cards.mtime → 差分
  ├ 新增      → 清该卡旧行 + 入库
  ├ mtime 变  → 清该卡旧行 + 入库
  ├ 磁盘已删  → 清该卡全部行
  └ 未变      → 跳过（不解析、不切词）
```

单卡入库逻辑抽成 `indexCardInto()`，全量与增量共用，避免两套逻辑漂移。

### 实测

| 场景 | 结果 |
|---|---|
| 无变化（508 卡） | 0 变更 / 38ms |
| 新增 1 张 | added=1 / 60ms |
| 修改 1 张 | updated=1 / 57ms |
| 删除 1 张 | deleted=1 / 53ms |
| 批量增 5 / 删 5 | 正确，孤立原子 0 |

对比全量 `build()`：964ms。**提速 25.4 倍。**

### 顺带修掉

- 向量陈旧回收：原子被删/重抽后旧向量留在 `vectors.f32` 只增不减。现在写出前按存活 id 过滤，实测回收 916 条，文件 24.2MB → 20.6MB。
- CLI 增加 `--sync` 子命令。

## 五、召回结果「可作依据」的修正（同日追加）

### 目标澄清

产品的目标不是问答式 RAG（问 → 答），而是**在动态工作中把召回回来的文本直接当依据**：
排障时定位、做新功能时判断能否复用、日常积累工程判断。

这要求每条结果都说得清「这条为什么相关、能当什么用」。

### 发现的问题

**问题 1：`hitAtoms` 排除了 title，导致「仅标题命中」退化成无关内容**

`hybridQuery()` 里 `WHERE nature != 'title'`，标题命中时 `hitAtoms` 为空，
展示层只能退回 `h.text`（该卡第一个非标题原子），给出的「依据」与查询无关。

实测：查询「排查静默失败应该怎么做」，第一条返回的依据是「只校验自己改的东西合法，
不等于目标系统读到了」——这句本身没错，但不是命中原因，读者无法判断相关性。

**问题 2：展示层把 title 也算进「结论」**

`factHits = hits.filter(a => a.nature !== 'body')` 包含 title，标题命中时
「结论」行就是把标题重复一遍，零信息量。

### 修改

| 改动 | 位置 |
|---|---|
| `atomInfo` 含 title，让 `hitAtoms` 反映真实命中 | `src/index.mjs` |
| `atomText` 继续排除 title，避免兜底文本退化成标题复读 | `src/index.mjs` |
| 展示层按 nature 分级：实质判断 > 正文段落 > 仅标题 | `src/server.mjs` |
| 仅标题命中时明确标注「非命中片段」，并给卡内代表内容供判断 | `src/server.mjs` |

### 效果

三条真实场景，每条都能直接当依据：

- 排障：「插件每次拉起 Chrome 都读该变量，只改 conf 不重启 = 不生效」
- 复用：「fs.rm 删库到 CREATE TABLE 之间存在窗口，期间查询会直接失败」
- 工程纪律：「排查静默失败的系统必须先补全每个环节的观测日志再下结论」

「仅标题匹配」的卡不再伪装成命中，明确提示需要 `memory_get` 确认。

### 已知未解

- RRF 融合分（0.03 量级）对读者没有参考价值，目前原样输出。
- 排序仍有优化空间：查询「插件改了代码不生效」的首条是 chrome-shell 主题，
  而更贴切的「补丁层改磁盘文件、进程仍加载旧模块」排在其后。属检索排序问题，
  与本次「依据可读性」是两件事。

## 六、让积累真正被用起来（同日追加）

### 问题：工具齐全，但没人用

三个工具（map / search / get）都已具备，设计也对（对标 aider 的 repo map）。
但插件注入的提示词是**被动触发**：

> 「当任务需要项目背景、历史决策……时，优先调用 memory_search」

问题在于 Agent 往往**不认为自己「需要」**。本次索引重构就是实例：直接从零调研，
而库里 11-13 已有记录：

> 「增量索引 sync-index.mjs：SQLite 全量重建 2–3 s，只编码缺失的原子，功能已验证」
> 「可选提速：capture 写卡后 spawn 一次 sync-index，延迟从 30 分钟降到几秒」

### 修改：改成主动触发

提示词改为「动手之前先查，而不是「觉得需要」才查」，并列出必须查的四个场景：

- 要改某个系统/插件/配置之前 → 查有无已知真源/已知坑/已做过的决策
- 遇到报错或异常 → 查错误关键词
- 设计新功能/新方案 → `memory_map` 看该领域已有积累，再决定是否从零做
- 任务面宽、无明确关键词 → `memory_map` 看全景

并说明三工具分工与「仅标题匹配」的含义。

### 顺手发现并修掉的两个问题

**1. 过时结论没人修正（机制问题，非代码 bug）**

检索「查询类型路由」时命中 11-02 的卡：「改进方向：按查询类型路由」。
但 11-13 实验已推翻它（路由 8/15 vs 统一 10/15，故 `QUERY_ROUTING` 默认关闭）。
卡上没有任何标记 —— 未来读到会重跑一遍失败的实验。

已用 `memory_update` 关闭该原子（`61c28ca6fb`）并追加修正记录。

**局限**：关闭原子只作用于 frontmatter，正文里同样的旧结论仍可能被命中。
彻底处理需要改正文，属破坏性编辑，未做。

**2. `ensureFresh` 的 60 秒缓存会误报「索引落后」（代码 bug）**

```
if (now - lastCheck < 60_000) return lastStale   // 直接返回旧判断
```

另一个进程（插件 / CLI）刚同步完索引，本进程在 60 秒内仍返回「索引落后 N 分钟」，
且不触发重新检查。实测 `.last-sync` 已是最新，提示仍说落后 9 分钟。

修法：缓存窗口内先读一次 STAMP（小文件读，比遍历全库便宜），STAMP 变了就立即重算。
验证：新进程检索不再误报。
