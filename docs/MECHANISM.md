# 机制

本文说明 memory-kb2 从头到尾怎么工作。每个设计选择都标注了它是在哪一轮实验里被定下来的，数据见 [BENCHMARK.md](./BENCHMARK.md)，过程见 [DEBUG-LOG.md](./DEBUG-LOG.md)。

---

## 0. 一句话

把本地 Markdown 卡片切成「原子」，为原子建 BM25 倒排索引与可选的向量索引；查询时两路召回、按 RRF 融合、去重后返回。整个过程在本地完成，只有可选的 embedding / rerank 会走远端 API。

---

## 1. 数据模型：卡片与原子

### 卡片（card）

一个 `.md` 文件就是一张卡。它有 frontmatter（标题、状态、时间）和正文。

卡片是**人写、人读**的单位：一张卡讲清一个知识点或一条记忆。

### 原子（atom）

卡片正文被切成若干**原子**，原子才是检索的基本单位。

为什么要切：一张卡可能有三段——排障过程、根因、结论。用户问「为什么报错」时命中的是「根因」那一段，但如果按整卡检索，命中的卡片里另外两段的词会稀释相关性，BM25 分数会变得没有区分度。

切分规则（`index.mjs`）：

- 按正文里的**小节标题**优先切分，识别的标题词表是一份正则：
  `排障 / 要点 / 结论 / 教训 / 根因 / 现象 / 原因 / 解决 / 修复 / 验证 / 注意 / 背景 / 方案 / 对比 / 步骤`
- 长度窗口 `BODY_MIN = 30` 到 `BODY_MAX = 400` 字。短于此不单独成原子（太碎，噪声大），长于此再切（一段百来字内的语义最集中）。
- 标题本身也作为一个原子入库（`nature='title'`），单独参与打分。

这个切法是在第 6 轮的「目标卡被 deleted 过滤」问题里改出来的——不是一开始就设计好的。

### 状态

卡片可以带 `status: deleted`（结论已被推翻、决策已撤销）。这类卡片**默认不返回**：一个已经不成立的结论被检索出来并当成事实使用，比检索不到更危险。需要查历史决策时用 `include_deleted: true` 显式打开（第 6、7 轮）。

## 2. 索引构建

`src/index.mjs` 做四件事：

### 2.1 遍历与解析

递归遍历 vault 下的 `*.md`，解析 frontmatter 与正文，切原子。

### 2.2 分词

中文没有天然词边界，这里用的是**二元组（bigram）+ 停用词**：

- 停用词表是一份紧凑的中文常用字集合（`的了是我在和有就都而及与着不也这那其等或从把被让给对为以中上下个人一`）
- 其余按二字滑窗切分

为什么不用分词器：零依赖。分词器要么带词典（体积大），要么要模型（慢且引入不稳定）。二元组在这个语料上够用——第 8 轮 59 条标注实测 top1 93.2%。

代价：召回偏宽松（会匹配到部分字序相同的片段）。这个代价由后面的 RRF 与去重环节吸收。

### 2.3 BM25

标准 Okapi BM25：

```
score(D,Q) = Σ_t IDF(t) · (f(t,D)·(k1+1)) / (f(t,D) + k1·(1 - b + b·|D|/avgdl))
```

- `k1 = 1.2`、`b = 0.75`，都是默认值
- **实测 k1 在 0.2–0.75 区间、b 在常见区间内改变，排序结果不变**（第 12 轮）。所以没有为这份语料调参——不是没调，是调了没用。

标题加权：标题原子的文本会以 `titleW` 倍权重参与打分。`titleW` 默认 1.3 还是 3.0，在 59 条标注上是打平的（54/59），选 3.0 是因为概念名查询（「什么是 X」）在 ×3 时略优。这条存疑见 [TUNING.md](./TUNING.md) 的「已知未解」。

### 2.4 向量（可选）

若配置了 embedding 凭据，索引时会给每个原子算向量，写入 `vectors.f32`。

端点走 OpenAI 兼容协议，默认指向通义千问。**没有凭据时会话会直接跳过这一步**，检索退回 BM25-only——这不是降级容错，是设计上就允许的形态（第 8 轮：工程库上向量并无收益）。

## 3. 检索链路

入口工具 `memory_search`。数据流：

```
query
  │
  ├─ BM25 召回 ──→ 候选集 A（topK）
  │
  └─ 向量召回 ──→ 候选集 B（topK）
                     │
              RRF 融合（A ∪ B）
                     │
                 内容去重
                     │
              归档过滤（status: deleted）
                     │
              limit 截断 → 返回
```

### 3.1 RRF 融合

Reciprocal Rank Fusion：对每个候选，把它在各路里的排名折算成分数再相加：

```
RRF(d) = Σ_r 1 / (k + rank_r(d))
```

`k` 取 60（常数，不用调）。选 RRF 而不是分数加权，是因为 BM25 的分数无上界、向量相似度在 [0,1]，两路尺度不可比——排名是唯一共同的度量。

第 18 轮的对照（M02 40 题）：BM25 单路 top8 45.0%、向量单路 57.5%、RRF 融合 top16 62.5%。融合确实有增量，但增量有多大取决于候选集够不够宽（见 3.2）。

### 3.2 候选池：自适应

**这是整份文档里最重要的一条。**

候选池是融合前每路取多少条。第 17 轮发现：池子太小时，重排器和融合都「看起来没用」——因为真正相关的候选根本不在池子里。

池深按库规模自适应：

```
pool = clamp(round(1.09 · √cards), 20, 80)
```

- 571 卡 → 26（工程库，仍在低档，实测 20 已足够）
- 5413 卡 → 80（聊天库，实测最优）
- 万卡级封顶 80，避免 rerank 成本随库规模线性上涨

系数 1.09 是从两个实测点拟合的，不是理论值；下限 20 是经验值（更浅的名额会被去重和时间窗吃掉）。

第 17 轮的对照（M02 40 题）：

| pool | 无 rerank 命中 | rerank 命中 | 覆盖（无/有） |
|---:|---:|---:|---|
| 20（旧默认） | 52.5% | 52.5% | 0.404 / 0.417 |
| 40 | 57.5% | 60.0% | 0.442 / 0.500 |
| 80 | 57.5% | **65.0%** | 0.467 / **0.588** |

同一条链路、同一份题，只把池子从 20 放到 80，聊天域召回从 48.3% 提到 65%。

### 3.3 内容去重

真实语料里有完整副本的卡片（同一段结论被抄进多张卡）。去重后 top5 的唯一内容从 3.60 条提升到 5.00 条（第 12 轮）——名额不被重复占满。

### 3.4 归档过滤

`status: deleted` 的卡片在**原子级**做过滤，不是在卡片级（第 7 轮修的）。卡片级过滤会漏掉「一张卡里部分结论已归档」的情况。

## 4. 重排（可选）

配置了 rerank 端点时可以对候选做精排。

**一条硬约束：送进重排的必须是完整 chunk，不能是单条原子。**

第 16 轮踩过这个坑：评测脚本把 `c.text`（40–100 字的单条原子）喂给 reranker，40 字判断相关性必然失真，导致「rerank 是负贡献」的错误结论。修正输入后重测：工程域 90% vs 无重排 92%（差 1 条题），聊天域完全相同——**不是负贡献，是无显著收益**。

默认关闭。理由是「没有收益却要多付约 0.8 秒延迟和重排费用」，不是「会变差」。这两个理由是不同的事，第 16 轮之前一直写错了。

候选深度：`pool` 决定送多少，`deep` 参数可再加深（成本约 2.5 倍）。

## 5. 场景档位：启动时判一次

不同语料的最优参数完全不同，所以服务启动时按语料特征判定一次档位（`detectProfile()`），而不是按查询内容切。

| 档位 | 判定条件 | limit | rerank | 向量 |
|---|---|---:|---|---|
| `wiki` | 平均标题 < 15 字 | 8 | 关 | 关 |
| `chat` | 原子/卡 ≤ 3 且正文均长 < 800 字 | 14 | 开 | 开 |
| `engineering` | 其余 | 5 | 关 | 开 |

判定读的是数据库里的统计量，不是配置：

```sql
SELECT COUNT(*) FROM cards                                  -- 卡数
SELECT AVG(LENGTH(title)) FROM cards                        -- 平均标题长度
SELECT COUNT(*) FROM atoms WHERE nature != 'title'          -- 原子数
SELECT AVG(LENGTH(text)) FROM atoms WHERE nature='body'     -- 正文原子均长
```

实测特征值：工程库 34.7 字标题 / 9.4 原子每卡；法学 wiki 6.8 字标题；聊天库 2.0 原子每卡 / 372 字正文。

**为什么是场景级而不是查询级**：查询级路由（同一个库内按问题类型切参数）被连续证伪两次——真实标注 90% vs 统一 92%（第 12 轮）。判据再细，也没有分给每一类查询足够的样本去验证它真的更好。

环境变量始终优先于自动档位：`MEM_TITLE_W` / `MEM_DEFAULT_LIMIT` / `MEM_RERANK` / `MEM_VECTOR` / `MEM_POOL`。

## 6. 一致性：索引不会悄悄过期

`ensureFresh()` 在每次检索前比对 vault 的最新 mtime 与索引 stamp：

- 有新内容 → 增量建索引
- 索引不可写（只读挂载） → 跳过，用旧索引继续服务，不报错

索引自身的一致性由 `scripts/selfcheck.mjs` 一条命令检查：卡数 / 原子数 / 向量条数是否自洽、归档卡规模、候选池不变量（池 5/20/80 的前 5 名必须完全一致）、延迟构成、服务层 top1/top3。退出码 0/1/2 分别对应全通过/有 FAIL/有 WARN。

候选池不变量是可证伪的设计断言：加深池子只应减少「过滤后名额不足」这类损失，**不应改变任何已排序结果**。第 19 轮用它验证过 64/64 查询的前 5 名完全一致。

## 7. 工具面

| 工具 | 用途 |
|---|---|
| `memory_search` | 检索。参数：`query`、`deep`（加深候选与重排）、`include_deleted`（含归档卡） |
| `memory_update` | 更新过时的卡：追加修正记录（保留历史），或把某条原子标记为不再成立 |
| `memory_stats` | 库规模、索引状态、延迟构成 |

`memory_update` 的存在不是可有可无的：记忆库最常见的问题不是检索不准，而是**检索到一条已经过时的结论**——端口变了、路径变了、方案被推翻了。追加而不是覆盖，是为了让「什么时候为什么改」也留在库里。
