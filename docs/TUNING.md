# 调参

本文记录每个参数为什么取这个值。所有数字都来自实测，实验过程见 [DEBUG-LOG.md](./DEBUG-LOG.md)，数据集见 [BENCHMARK.md](./BENCHMARK.md)。

**一份说明**：这份表里有些参数的「依据」是**证伪**——实验做了，结论是「没用，关掉」。这类也保留，因为下一个改它的人需要知道这里已经试过。

## 2. 逐个参数的依据

### `MEM_VECTOR` —— 向量开关

三个域三种结论，所以它不能是一个全局默认：

| 域 | 结论 | 数据 |
|---|---|---|
| 工程库 | 真实问法 top3 +2pp | BM25 ×3.0 是 top3 98%，hybrid 是 **100%**；top1 相同（92%） |
| 聊天库 | 明确正收益 | 向量单路 57.5% vs BM25 单路 45%（M02 40 题） |
| 法学 wiki | **负收益，必须关** | dense 0.434 < BM25 0.529；概念名 recall@1 98.9% |

**关于「工程库向量零增益」的更正（2026-11-20 复测）**：第 2 轮曾用 leave-one-out 得到「加入向量后一位未变」，据此写下「零增益」。复测发现这是**天花板效应**，不是向量无效：

| 指标 | 结果 |
|---|---|
| BM25 top1 命中自己 | 40 / 40 |
| hybrid top1 命中自己 | 40 / 40 |
| 两路结果完全一致 | 1 / 40 |
| 两路有差异 | 39 / 40 |

向量路改变了 40 次里的 39 次结果，但 leave-one-out 用卡正文当查询，BM25 已经 100% 命中，向量没有提升空间。**真实问法（措辞与卡片不同）才是向量该发挥的场景，那里 top3 有 +2pp。**

另外，向量路本身工作正常：用卡自身向量自查询，自身 1.0000、同主题 0.63，区分度清晰。

法学 wiki 的负收益不受此影响——那是在真实概念名查询上测的，方向相反且幅度明确。

### `MEM_RERANK` —— 重排开关

**默认关闭，但理由是「无显著收益 + 高延迟」，不是「负贡献」。**

修正评测输入后的对照（第 16 轮，59 条标注）：

| 域 | 无 rerank | 有 rerank | 延迟 |
|---|---:|---:|---|
| 工程 top1 | 92% | 90%（差 1 条题） | 0.37s → 1.2s |
| 工程 top3 | 100% | 98% | |
| 聊天 M02 命中 | 48.3% | 48.3% | |

工程域少的那 2 个百分点是 1 条题，在 59 条样本上是噪声。聊天域完全相同。

**但在候选池够大时，重排是有增益的**（第 17 轮）：pool 80 时聊天域命中从 57.5% → 65.0%。所以「rerank 无效」这个结论只在 pool=20 的前提下成立——池子太浅，重排没有可换的好货。

### `MEM_POOL` —— 候选池深度

自适应公式与系数拟合依据见 [MECHANISM.md §3.2](./MECHANISM.md)。

关键数据（第 17 轮，M02 40 题）：

| pool | 无 rerank | 有 rerank | 覆盖增量 |
|---:|---:|---:|---:|
| 20 | 52.5% | 52.5% | +0.013 |
| 40 | 57.5% | 60.0% | +0.058 |
| 80 | 57.5% | 65.0% | +0.121 |

**`pool` 与 `rerank` 必须一起看。** 单独调任何一个都会得到「没用」的错误结论。

### `MEM_DEFAULT_LIMIT` —— 返回条数

聊天档从 8 提到 14：M01 前 30 题 evidence 命中 50% → 53.3%，覆盖率 0.125 → 0.25（第 12 轮）。

工程档保持 5：571 卡的库里通常 1–3 条就能定位，返回更多只是增加阅读成本。

### `MEM_TITLE_W` —— 标题权重

1.3 与 3.0 在 59 条标注上打平（54/59）。选 3.0 的理由是概念名查询（「什么是 X」）略优，**但这条证据强度弱**，见第 5 节。

### `MEM_BM25F` —— 字段加权（已证伪）

想法很合理：标题和正文分别加权，像 BM25F 那样。实现了，也测了（第 13–15 轮）：

| 配置 | 法学 wiki 准确率 |
|---|---:|
| 纯 BM25（titleW 单路近似） | 98.9% |
| BM25F（title×3 + body×1） | 98.4% |
| BM25F（body 权重压到 0.2） | 98.4% |

即使把正文权重压到 0.2，仍然低于纯 BM25。原因：这份语料的卡片是**短标题 + 完整正文**结构，正文里的字段加权没有额外信息，只是打散了标题的主导地位。

保持 `MEM_BM25F=0`，不再尝试。

### `MEM_QUERY_ROUTING` —— 查询级路由（已证伪）

按查询类型切换参数（事实查询 vs 概念查询）。真实标注 90% vs 统一参数 92%——更细的路由反而更差。

推测原因：每类查询的样本量不足以验证「这一类更适合那组参数」，所谓路由只是在小样本上过拟合。

保留 `MEM_QUERY_ROUTING=1` 作为实验开关，默认关闭。

### `k1` / `b`

实测 k1 在 0.2–0.75、b 在常见区间内改变，排序结果不变（第 12 轮）。保持 Okapi 默认值 1.2 / 0.75。

## 3. 场景档位

判定规则与特征值见 [MECHANISM.md §5](./MECHANISM.md)。这里补充**为什么是这个阈值**：

| 档位 | 阈值 | 实测特征值 | 间距 |
|---|---|---|---|
| `wiki` | 平均标题 < 15 字 | 法学 wiki 6.8 字 | 8.2 字余量 |
| `chat` | 原子/卡 ≤ 3 且正文均长 < 800 字 | 聊天库 2.0 / 372 字 | 1.0 / 428 字余量 |
| `engineering` | 其余 | 工程库 9.4 / 长正文 | — |

阈值取在两档实测值的中间地带，不是精确边界。三档的实测特征值差距都在 8 字 / 428 字以上，容错空间足够——但如果你的语料落在这个灰区，用环境变量显式指定，不要指望自动判定。

档位判定结果会写在检索结果的头部（如 `engineering档·统一·标题权×3`），便于现场确认。

## 4. 切换方式

```bash
# 工程档（默认）
node src/server.mjs

# 聊天档
MEM_DEFAULT_LIMIT=14 MEM_TITLE_W=1.3 MEM_RERANK=1 node src/server.mjs

# 法学 wiki 档：需要关向量（让环境里没有 embedding 凭据）
node src/server.mjs
```

**注意：显式环境变量优先于自动档位。** 如果你设了 `MEM_DEFAULT_LIMIT`，自动判定就不会覆盖它。

## 5. 已知未解

诚实列出没搞清楚的部分：

1. **聊天域 evidence 命中 48.3%**，远低于工程库的 92%。来自题目性质——要想起多轮对话里的细节，提升空间在名额分配而不是重排。没解决。
2. **`MEM_TITLE_W` 的 1.3 vs 3.0 证据弱**。59 条标注打平，选 3.0 只有「概念名查询略优」这一条弱证据。如果你的语料更偏事实检索，1.3 可能更合适。
3. **法学档的 BM25F 没有真正实现**。现在的 `titleW` 只是标题那一路的近似，不是完整的多字段加权。做过（第 13–15 轮），被证伪，所以没继续。
4. **自适应池的系数 1.09 只有两个拟合点**（571 卡与 5413 卡）。中间规模的库可能不是最优。
5. **多跳检索只到第一跳基线**（第 20 轮），没有实现多轮改写再检索。
