# 起源与演变

这份文档记录 memory-kb2 的每一个决策：为什么做、加了什么、撤了什么、每次改变的依据是什么。材料来自 2026-11-13 至 11-16 的实验会话。

它不是变更日志（[DEBUG-LOG](./DEBUG-LOG.md) 按轮次记录），而是**按决策组织**——同一件事的添加、修正、放弃放在一起看。

---

## 0. 起点

前身 [memory-eternal](https://github.com/EternalNight996/dsh-memory-eternal) 解决的是「沉淀」：对话结束，把有价值的内容写成 Markdown 卡。

「记得」不等于「找得到」。卡片到几百张之后，塞进 prompt 放不下、靠目录找依赖记忆、关键词搜索会捞出不相关段落。kb2 要解决的是这一层。

---

## 1. 第一次撞墙：两个库给出相反的答案

2026-11-13，对两个库做同一件事——把标题权重 `titleW` 从 ×1.0 扫到 ×4.0：

| titleW | 工程库 leave-one-out @1 | 法学库 @1 |
|---|---:|---:|
| ×1.0 | **98.8%** | 98.1% |
| ×1.3 | 98.6% | 98.0% |
| ×2.0 | 98.2% | 97.8% |
| ×3.0 | 95.4% | 97.3% |
| ×4.0 | 94.6% | 96.5% |

工程库上权重越大越差（98.8% → 94.6%）。但同一批材料里，法学 wiki 的评测给出相反结论：**BM25F（标题×3）最好**，MRR 0.556 > BM25 0.529 > dense 0.434。

两个结论都对，因为**查询的构造方式不同**：

- 工程库的 leave-one-out，查询取自**卡片正文的一段话**。标题与这段话无关，加权只会把错误的东西推上来。
- 法学 wiki 的评测，查询是**概念名**（`善意取得`、`正当防卫`）。标题本身就是答案，加权自然有效。

这一轮没有改任何参数。它改的是从此以后怎么造评测。**指标只描述「在它的查询构造下谁更好」，不描述真实问法。**

## 2. 参数校准：1.0 / 1.3 / 3.0 的三次逼近

### 第 3 轮（15 条）：看到 ×3 更优

| 配置 | top1 |
|---|---:|
| BM25 ×1.0 | 53% |
| BM25 ×1.3（旧默认） | 60% |
| **BM25 ×3.0** | **67%** |
| 查询路由（概念×3 / 描述×1.0） | 53% |

看起来 ×3 明显更好。**如果停在这里，会把 3.0 定为默认——而它后来被证明是假象。**

### 第 4 轮（32 条）：假象消失

| 配置 | top1 | top3 |
|---|---:|---:|
| BM25 ×1.0 | 78% | 88% |
| BM25 ×1.3 | **81%** | 88% |
| BM25 ×3.0 | **81%** | 88% |
| hybrid ×1.3 | 78% | 88% |
| 查询路由 | 78% | 88% |

**×1.3 与 ×3.0 完全打平（都 26/32）**，只比 ×1.0 多一条。第 3 轮那 1 条题的差距撑不住扩样。

### 第 8 轮（59 条）：定论

| 配置 | top1 | top3 |
|---|---:|---:|
| BM25 ×1.0 | 88% | 95% |
| BM25 ×1.3 | 92% | 97% |
| **BM25 ×3.0** | **92%** | **98%** |
| hybrid ×1.3（含向量） | **92%** | **100%** |

top1 上仍然打平。

### 最终取值与理由

定 3.0，理由不是「更好」，是三条：

1. top1 打平，**没有统计上可分辨的损失**
2. 概念名查询在 ×3 时略优——这一侧的证据来自规模更大的法学评测
3. 工程库的卡片以标题承载概念（标题均长 34.7 字、原子/卡 9.4），与概念名查询同构

这条结论在 [TUNING.md](./TUNING.md) 里被标为「证据弱」。它就是弱的：如果语料更偏事实检索，1.3 同样合理。

## 3. 功能账本：加了什么、撤了什么

### 保留的

| 功能 | 加入依据 | 现状 |
|---|---|---|
| **内容级去重** | 真实工程库发现 571 张卡在 `00-Inbox/记忆卡/` 有完整副本，同内容互占名额。去重后 top5 唯一内容 3.60 → 5.00 | 核心 |
| **归档卡原子级过滤** | `include_deleted` 初版只放开卡级过滤，deleted 卡的原子仍被 `active=0` 挡住。修成原子级后归档组 4/4 命中 | 核心 |
| **titleW 参数化** | 见上一节，从写死改为可配，profile 决定取值 | 核心 |
| **向量路** | 工程库零增益、聊天 +6.7pp、法学 −18% MRR。三域结论不同，所以做成可选路：开不开由 profile 决定 | 核心，按档开关 |
| **RRF 融合** | 两路分数尺度不可比（BM25 无上界、向量 [0,1]），排名是唯一共同度量 | 核心 |
| **自适应候选池** | 池深 20 → 80，聊天域命中 52.5% → 65%。公式 `clamp(round(1.09·√cards), 20, 80)` 由 571 与 5413 两个实测点拟合 | 核心 |
| **三档 profile** | 同一改动在不同域方向相反，见第 5 节 | 核心 |
| **场景自动识别** | 换库不必手改环境变量；服务启动时读语料统计量判一次 | 核心 |
| **多 MCP 实例** | 一个进程只能绑一个库（`VAULT`/`DB_PATH` 是模块级单例）。改成工厂的代价是半天到一天且动核心模块；加实例只要配置 | 部署方式 |
| **查询向量缓存** | embedding 往返占检索延迟九成；同一 query 向量恒定。实测命中 54 ms，净省 191 ms（CI [165,227]） | 核心（默认开） |
| **检索结果缓存** | 向量缓存之后本地链路仍剩约 55 ms；key 带 `meta.built_at`，重建索引即失效。实测命中 1 ms，返回 64/64 一致 | 核心（默认开） |
| **scope 收窄** | 卡片 `scope:` 入索引，`memory_search(scope:[...])` 只返回该域。PrecisionMemBench 13.2% → 23.7%，与别名叠加 26.3%（+10 条题，0 回归） | 核心（显式参数，不传不过滤） |
| **法学正文入索引** | 法学卡章节名（体系位置/内容/效果/连线…）不在默认词表里，385 万字正文此前完全不可检索。实测正文细节 top1 87.7% → 97.6%（+93 条题），概念名 recall 不降 | 核心（`MEM_BODY_SECTIONS` 注入，默认词表不变） |

### 加过又撤掉的

| 功能 | 尝试时的结果 | 撤回原因 |
|---|---|---|
| **查询类型路由** | 15 条 53%、32 条 78%、59 条 90%，一直低于统一参数（92%） | 分类器本身 10/10 正确，但每类查询样本不足以验证「这一类更适合那组参数」，路由只是小样本过拟合 |
| **标题覆盖率独立路 + RRF** | 4 条失败案例 0/4 修复，权重 0.5/1.0/2.0 全试过 | 失败的真因不是排序，是目标卡被 `status: deleted` 过滤（见第 4 节） |
| **标题乘法先验** | `score *= 1 + 0.9×覆盖率`，top1 一字未变 | 目标卡的 BM25 基数太低，乘系数追不上 |
| **k1 / b 调参** | k1 扫 0.2–0.75、b 常见区间，排序结果不变 | 这份语料对这两个参数不敏感，保持 Okapi 默认 |
| **BM25F 字段加权** | 法学 wiki +17.5pp（模拟）→ 真实实现 −21.7pp；细化后 77.2%，仍低于纯 BM25 的 98.9% | 语料是「短标题 + 完整正文」，正文加权没有额外信息，只打散标题主导地位 |
| **rerank 默认开启** | 严格口径 66%，放宽后 73%，修正输入后 90%（vs 无重排 92%） | 无显著收益，多付约 0.8 秒和重排费用。**不是负贡献**——那个结论是评测输入错误造成的 |
| **多角度 BM25（句法切分）** | 证据命中 50.0% → 50.0% | 按标点切子句，切出的片段与原句共享同一批 bigram，没有新增信息 |
| **事实级原子** | 预估原子数从 21129 降到 7000–15000 | 原子变少不解决「一卡只占一个名额」的问题；重叠聚类更直接 |
| **按命中位置截取** | M01 1456 条里原文超 300 字的 0 条；M02 只有 11.4% | 89% 的条目根本不到 300 字，截哪里都一样 |
| **时间维度参与检索** | 未实施 | 卡片 mtime、frontmatter 时间、正文提到的时间经常三者不一致，拿它做检索维度等于把噪声写进索引 |
| **多原子重叠 diff** | 可行但边界窄 | 只能在检索后处理层做，且必须「呈现差异」而不是「下结论」；未落地 |
| **反向验证共识门槛** | 桥接精度 3.0% → 0.8% / 0.8% / 0.9% | seed 是同一道题的检索结果，彼此高度重叠，「被几个 seed 支持」几乎对所有候选都成立，起不到区分作用 |
| **抽取式改写（别名扩展）** | PrecisionMemBench 13.2% → 14.5%（+1 条题），工程库 93.2/100 不变 | 收益落在 ±2 条题的噪声带内。保留 `MEM_ALIAS=1` 与别名表，**不默认开** |
| **聊天最近窗口保底再调** | 0 vs 6 轮：M02 120 条 unit 级配对 +0.9 pp（10 过 / 9 不过），95% 区间 [−14.0, +12.2] | 无效。窗口一直开着（`MYKB2_RECENT_TURNS=6`），这条通道不产生可测收益，停止投入 |

## 4. 三次认知修正

这三条不是功能改动，但每一条都改变了对系统的判断。

### 修正一：天花板来自归档卡，不是排序

32 条标注里有 4 条必然失败——目标卡是 `status: deleted`（571 张卡里 85 张，14.9%），检索按设计不返回。

排除这 4 条后，top1 从 81% 变成 **93%**。真实水平被误判了两轮。

### 修正二：rerank 的「负贡献」是评测 bug

第 10 轮把 rerank 默认关掉，依据是「top1 从 92% 掉到 73%」。

第 16 轮解剖失败案例发现：送给 rerank 的 doc 只有 40 字——评测脚本用了 `c.text`（单条命中原子），而生产用的是 `summaryOf`（正文前 200 字）。**生产逻辑是对的，评测脚本错了。**

修正输入后重测：工程域 90% vs 无重排 92%（差 1 条题），聊天域完全相同。**不是负贡献，是无显著收益。**

默认关闭的结论不变，但理由必须改：不是「会变差」，是「没有收益却要多付 0.8 秒和重排费用」。

### 修正三：真瓶颈是候选池

第 11 轮认为 rerank 在聊天域「零贡献」。第 17 轮追查发现：候选池只有 20，真正相关的证据挤不进池子，重排面对空池无能为力。

池深 20 → 80：命中 52.5% → **65%**、覆盖 0.404 → 0.588。不用改算法。

## 5. 架构原则：引擎全能力，profile 只调参

2026-11-13 晚的第一版拆法把「工程 / 法学 / 聊天」当成三个系统，各自有最优参数。结果 kb2 成了功能最少的那一个——只需要 BM25 和 title×1.3。

这个拆法是错的。修订后的分层：

| 层 | 内容 | 归属 |
|---|---|---|
| 索引层 | 二元组分词、BM25/BM25F、字段加权、增量重建 | kb2 核心 |
| 召回层 | BM25 路 + 向量路 + RRF 融合 | kb2 核心 |
| 排序层 | rerank、标题先验、分数融合 | kb2 核心 |
| 名额层 | 内容级去重、重叠聚类、limit | kb2 核心 |
| 路由层 | 场景判定 → 选参数 | kb2 核心 |
| 档位 | 工程 / 法学 / 聊天 三套参数 | **profile，不是代码分叉** |

**硬规则：任何在某个域验证过的能力，先问「能不能进核心」，再谈「要不要只在某个 profile 开」。**

向量路径是这条规则的实例：它在工程库零增益、聊天 +6.7pp、法学负收益——三种结论并存。但它仍然是**核心里的一条可选路**，不是「只在 chat 存在的功能」。

## 6. 三档是怎么形成的

不是设计出来的，是三次「方向相反」逼出来的：

| 档位 | 关键证据 | 结论 |
|---|---|---|
| **法学 wiki** | BM25F 0.556 > BM25 0.529 > dense 0.434；概念名 recall@1 98.9% | 概念名查询，标题即答案；向量引入近义干扰，关 |
| **聊天 chat** | 向量单路 57.5% > BM25 单路 45%；但 M02 证据命中 48.3% 见顶 | 长对话要想起细节，召回宽度比排序精度重要 |
| **工程默认** | top1 93.2% / top3 100%（59 条） | 短标题 + 完整正文，精确找那张卡 |

同一个改动在不同域方向相反的例子：

| 改动 | 法学 wiki | 工程库 |
|---|---:|---:|
| BM25F（标题×3 + 正文×1） | **+17.5pp** | **−7pp** |
| 向量 | −18% MRR | 零增益 |
| rerank | 未测 | 无显著收益 |

所以「一套参数打天下」不是简化，是错误。v0.4.0 把它做成了启动时自动识别：读标题均长、原子/卡、正文均长，判一次档位。

## 7. 方法论

1. **指标会骗人，而且骗法很具体。** leave-one-out 的查询取自卡正文，天然惩罚标题加权；rerank 评测喂 40 字碎片，天然显示负贡献；候选池只有 20，任何更聪明的排序都看不出差别。
2. **样本量不到 50 不要定参数。** 15 条的「×3 更好」在 32 条上消失；40 条的「向量让 top1 掉 3pp」在 59 条上打平。
3. **能力进核心，参数进 profile。**
4. **先查观测手段，再查算法。** 二十轮里五次「组件没用」，四次最后追溯到评测怎么造、怎么喂。
