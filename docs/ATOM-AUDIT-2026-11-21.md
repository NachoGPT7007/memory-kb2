`npm run audit` 已成为可重复命令。生产库首跑：

## 1. 这个数字和交接文档对不上，原因查清了

NEXT-SESSION-2026-11-21.md 记的是「实测 93.3% pass；真问题只有 7 条『标题列表被当原子』」。差异来源：

| 口径 | pass 率 |
|---|---|
| 当次（推测只覆盖近期沉淀、走 `normalizeCard` 的卡） | 93.3% |
| 本次（全库、含历史卡与早期导入） | 80.0% |

依据：pending 卡的原子 100% pass；769 条问题原子按卡聚合后，集中在 `03-Knowledge/*`、`08-Mistakes/*` 等早期 approved 卡上（单卡最多 8 条）。

这不是「质量突然变差」，是**审计范围不同**。质量规则只在一条入库通道（`normalizeCard`）上生效，历史数据没有回填治理。

## 2. 四类问题

| 原因 | 条数 | 说明 |
|---|---:|---|
| `list-marker` | 390 | 以 `-`、`1.`、`①` 开头——列表项被当成判断 |
| `arrow` | 302 | 含 `→` 等箭头（流程描述） |
| `half-sentence` | 74 | 以「和/与/、/：」结尾，半截句 |
| `title-list` | 40 | 「标题：甲、乙、丙」且冒号前是短语——清单被当成一条判断 |

前两类本来就在 `capture.js` 的 `normalizeCard` 里被明令丢弃（`text.length` 12–120、`/[→←↑↓]/` 直接 `return null`）。这批原子能进库，说明它们**不是走那条通道进来的**——早期导入、手工写入或其他 agent 直写 vault。

## 3. 为什么只出报告、不自动改写

正则判得出「这条写得不好」，判不出「应该怎么改」。自动改写要用模型，而模型改写会引入对话里没有的表述——沉淀提示词里明令禁止这件事（「不得引入对话里没有的术语、数字、路径或结论」）。

所以这里只给三分类与卡级聚合，改不改由人定。

## 4. 用法

```bash
npm run audit                      # 生产库
npm run audit -- --only pending    # 只看待审卡（给批/驳做依据）
npm run audit -- --json            # 机器可读
npm run audit -- --samples 20      # 每类样本数
node scripts/audit-atoms.mjs --vault /path/to/vault
```

退出码：0 全 pass；2 有问题（可直接接 CI 或定时任务）。

## 5. 规则与阈值

| 判定 | 条件 |
|---|---|
| too_coarse | 长度 > 120 字；或 > 50 字且含 ≥3 段并列（`；` 分隔） |
| needs_rewrite | 长度 < 12；列表符号/编号开头；半截句结尾；含箭头；标题后接清单；纯符号且 < 20 字 |
| pass | 其余 |

长度按**字符**（汉字）计，不按空格——LMC-5 特别标注过：按空格会给中文原子算出接近 0 的长度。

阈值是拍出来的，但有一条实测依据：`multi-clause` 原定 80 字，实测「端口，；路径，；凭据，；索引，；缓存」这类 65 字 5 段的串会被放过，改为 50 字。

## 5.1 规则的第一版有误判，已修（同一轮内）

第一版跑出 21.1%，抽样本人工复核时发现两类误判：

| 误判 | 例子 | 修法 |
|---|---|---|
| 「的」结尾一律判半截句 | 「lib/ 是作者编译后放进仓库的成品…不是本地改的」——中文「是…的」完整判断句 | 去掉「的」，只判标点与连接词结尾 |
| 冒号后带列举就判标题清单 | 「它同时承载：邮箱根、身份根、服务根」——完整主谓句 | 要求冒号前 ≤10 字且不含判断动词 |

修正后 pass 78.9% → **80.0%**，`half-sentence` 89→74、`title-list` 76→40。

这条写在这里是因为：**数字变了两次，第一次那版不能引用**。

## 5.2 它到底有没有害（只读诊断）

脚本 `scripts/diagnose-atom-quality-impact.mjs`，输入取自真实召回账本 `memory-recall-ledger.jsonl`，检索走 hybridQuery + 查询向量，「依据」模拟方式与 `src/server.mjs` 一致（按 boundary→fact→state→plan 取前 6 条）。

| 指标 | 数值 |
|---|---|
| 有效查询 | 44 条（账本唯一查询数，**未达 50 条门槛**） |
| 进入「依据」的原子 | 721 条 |
| 其中质量不合格 | 89 条（**12.3%**） |
| 至少含一条不合格依据的查询 | 22 / 44（**50.0%**） |

结论只能到「观察」级：一半查询会看到至少一条写法不合格的依据，但样本 44 条不够定论。

**另一个更强的信号**：诊断样本里出现了明显不相关的召回——查「华政本科毕业论文规范」返回了 harness 工程卡的依据。那是排序问题，不是原子质量问题。修原子质量不解决它。

## 5.3 该不该改造历史卡：不改，理由有三

**一、问题原子里 86% 是 fact，内容是「步骤」不是垃圾。**

| nature | 问题原子 | 该 nature 总数 | 占比 |
|---|---:|---:|---:|
| fact | 632 | 3085 | 20.5% |
| boundary | 81 | 450 | 18.0% |
| state | 12 | 81 | 14.8% |
| plan | 6 | 48 | 12.5% |

抽查样本全是「1. 浏览器打开 → 应跳登录页」「客户端 → 设置 → Cloud Sync」这类操作序列。它们**有信息**，只是不该以「一句可独立成立的判断」的形式存在。

**二、根因在 nature 枚举缺一类，不在历史数据。** 当前只有 fact / boundary / state / plan / preference，模型遇到流程没有合适标签，只能塞进 fact。要治，应该先加 `step` 类，否则重写一遍还是会被塞回 fact。

**三、改造成本与收益不对等。** 731 条意味着重写卡片正文（破坏性编辑），而收益未被证明——上面那 50% 里有相当一部分是排序问题，不是原子问题。

### 更轻的两个方向（未做）

1. **检索层降权**：`needs_rewrite` 原子在排序里乘 0.8，可逆、可测、不碰真源
2. **补 nature=step**：提示词加一条「步骤/操作序列不要写成判断原子」，需要同步改 nature 白名单、索引与展示
