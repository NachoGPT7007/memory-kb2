# 与企业级 RAG 的架构差异

这份文档回答一个问题：**为什么 kb2 做了检索，成绩却没有超过官方 BM25 基线？**

答案是结构性的：kb2 只做了 RAG 链路里的一段，而且缺了两段对成绩影响最大的。下面是逐环节对比。

---

## 1. 完整环节对比

| # | 环节 | 企业级 RAG（Qwen RAG / 通用方案） | kb2 | 差距 |
|---|---|---|---|---|
| 1 | 文档解析 | PDF / Word / HTML / 表格 / 公式 / 图片 / 版面分析 | **只吃 Markdown**（`parseCardFile` 解析 frontmatter + 正文） | **大** |
| 2 | 分块 | 语义分块、父子块、重叠窗口、按标题层级 | 按小节标题 + 30–400 字长度窗切原子 | 中：无父子块与重叠 |
| 3 | 元数据 | 时间、类型、来源、**权限**、租户 | 有 `status` / 时间 / 类型，**无权限、无租户** | **大** |
| 4 | 向量化 | 专用模型 + 批量 + 缓存 | qwen3.7-text-embedding，1024 维，磁盘 `.f32` | 小：够用 |
| 5 | 索引 | 向量库（Milvus/pgvector）+ 倒排 + 图 | SQLite 倒排 + `vectors.f32` 全量加载 | 小：万卡级会成问题 |
| 6 | **Query 理解** | **改写 / HyDE / 多查询 / step-back / 意图分类** | **无**——query 原样进检索 | **致命** |
| 7 | 检索 | 多路：向量 + 关键词 + 元数据过滤 + 图召回 | 两路：BM25 + 向量 + RRF | 中：缺元数据过滤 |
| 8 | 重排 | 通常必开 | 有，**默认关**（工程库实测无收益） | 小：有依据的选择 |
| 9 | **上下文组装** | **token 预算、lost-in-the-middle 排序、压缩、去重** | 去重 + limit 截断 | **大** |
| 10 | **最近窗口保底** | **常驻最近 N 轮原文**（保证「刚说过」的一定在） | **无**——适配器只有 `search`，不拼最近轮次 | **致命** |
| 11 | 生成 | LLM + 提示词工程 + few-shot | **不做**（设计如此，交给 MCP 客户端） | 设计边界 |
| 12 | 评估 | RAGAS（faithfulness / context precision）、人工 | top1/top3、PrecisionMemBench 断言 | 中 |
| 13 | 反馈闭环 | badcase 回流、点击数据、A/B | 无 | **大** |
| 14 | 多租户 | user_id / 租户隔离、文档级 ACL | **无** | **大** |

---

## 2. 三个「完全没有」的

### 2.1 Query 理解与改写 —— 最致命

企业 RAG 在这一层做的事：

- **改写**：把口语化简成检索词（「我之前那个部署的事」→「部署 流程 配置」）
- **HyDE**：先生成假设答案，再用它检索（对语义检索提升明显）
- **多查询**：一次问句扩成 3–5 个变体，各自检索后合并
- **step-back**：先把问题抽象一层再检索
- **意图分类**：判断是找事实、找流程、还是找历史决策

kb2 **一条都没有**。query 原样进入 BM25 与向量。

这是成绩差距的**第一主因**：卡片措辞与用户问法之间的鸿沟，全靠字面重叠去碰。

### 2.2 最近窗口保底 —— 第二主因

官方 BM25 基线（`sentinel-bm25-recent6`）的结构是：

```
上下文 = BM25 检索的 top-k + 最近 6 轮的原文
```

「最近 6 轮」是**保底**，不依赖检索——凡是问「刚才说过什么」，答案一定在上下文里。

kb2 的适配器只有 `search`，**不拼最近轮次**。所以：

- 问「刚说的那个约定」→ 检索可能命中，也可能不命中
- 官方基线 → 最近 6 轮一定在，必然命中

**这就是 kb2 在 2.2 上低于基线的结构性原因**：它主动放弃了一条保底通道。

### 2.3 元数据过滤 —— 直接影响 PrecisionMemBench

belief 自带 `scope: [domain:code]`、`user_id`。kb2 检索时不看这些字段：

- 问编程问题，会把写作域的卡一并捞出来 → 撞上 `shouldOnlyInclude` 断言
- 跨用户样本（`b-other-user-leak-check`）必然违规

这不是调参问题，是**检索时没有过滤维度**。

## 3. 为什么「魔改 Qwen RAG 反而不如 Qwen RAG」

Qwen RAG 的价值不在检索算法——BM25 与向量都是公开方法，谁都能实现。它的价值在**链路工程**：

| 环节 | 谁在承担 | 谁给出了价值 |
|---|---|---|
| Query 改写 | Qwen RAG 内置 | **kb2 没有** |
| 最近窗口保底 | Qwen RAG 内置 | **kb2 没有** |
| 上下文组装与压缩 | Qwen RAG 内置 | kb2 只有去重 + limit |
| 重排 | Qwen RAG 内置且默认开 | kb2 默认关（有实测依据，但对长对话不利） |
| 生成提示词 | Qwen RAG 内置 | kb2 交给外部 |

**只保留检索段、其余自己重写，等于把 Qwen RAG 的工程价值砍掉，只留了最容易复现的那部分。**

而且 kb2 在检索段上确实是**有改进**的：候选池自适应、内容去重、三档参数。这些在 PrecisionMemBench 与自建标注上都有数字支撑。

问题在于：**改进都在「排序精度」上，而差距在「召回保底」与「查询理解」上。**

排序做到 93.2% top1，在工程库这种短标题语料上已经到顶；但聊天/对话语料里，瓶颈是「答案根本没进候选集」——那一段不归排序管。

---

## 4. 如果只补两刀

按对成绩的影响排序：

### 第一刀：最近窗口保底（约 30 行）

在适配器/服务层加一条独立通道：

```
上下文 = 最近 N 轮原文（保底） + 检索结果（补充）
```

依据：官方 BM25 基线靠这一条就拿到 M01 37.4 / M02 45.1，而 kb2 现在是 34.7 / 39.2。**补上这条至少追平基线。**

代价：多占上下文 token；需要按库类型决定 N（工程库 N=0，聊天库 N=6）。

### 第二刀：Query 改写（约 100–200 行，或一次 LLM 调用）

最小可行版本：**一次轻量改写请求**，把口语化问题转成检索关键词，然后：

- 原 query 与改写 query 各检索一次，结果合并（RRF）
- 或者只改写、不合并（成本减半）

依据：2.2 的失败分析显示 33.4% 的题「答案依据根本没进提示词」——这是召回问题，而改写是提高召回最直接的手段。

代价：每次检索多一次 LLM 调用（约 ¥0.002），以及一次延迟叠加。

### 第三刀（可选）：元数据过滤

给卡加 `scope` / `user_id` 字段，检索时按调用方传入的 scope 过滤。

依据：PrecisionMemBench 的 23 个 Alias + 12 个 Scope case 直接受益。

---

## 5. 不该补的（已经验证过无效）

| 方向 | 为什么不做 |
|---|---|
| 多跳 / 关系扩展 | 桥接精度 1–3%，top3 已 100% 只有下降风险 |
| BM25F 字段加权 | 模拟 +17.5pp，真实实现 −21.7pp |
| 查询级路由 | 59 条上 90% vs 统一 92% |
| 更深的候选池（>80） | 万卡级封顶，边际收益趋零 |
| 重排默认开 | 长文档有增益，但工程库无收益且多付 0.8 秒 |

---

## 6. 一句话总结

**kb2 的检索段是可以的（工程库 top1 93.2% 到顶），但它是一条缺了两端的链路：前面缺查询理解，后面缺上下文保底。**

企业 RAG 的优势不在算法，在这两端。把它们补上，才谈得上「比 Qwen RAG 好」；不补，就只能是「检索质量不错，但端到端打不过」。
