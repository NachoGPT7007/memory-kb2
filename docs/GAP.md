# 与企业级 RAG 的架构差异（个人使用视角）

这份文档回答：**为什么 kb2 做了检索，成绩却没有超过官方 BM25 基线？**

先说结论：按通用企业 RAG 的 14 个环节对比，kb2 缺 10 项——但那 10 项里绝大多数是**规模问题**，个人使用不该背。真正影响成绩的只有三条。

---

## 0. 个人使用的前提

| 前提 | 影响 |
|---|---|
| 语料是 Markdown 卡片 | 不需要 PDF / Word / 表格解析 |
| 单人使用 | 不需要多租户、ACL、权限模型 |
| 库规模 571–5413 卡 | 不需要外置向量库（24MB 全量加载够用） |
| 没有线上流量 | 不需要反馈闭环、A/B、灰度 |
| 有自建评测 | 不需要 RAGAS 这类自动评估框架 |

在这个前提下，「企业有而 kb2 没有」的十项不是差距，是**不需要**。

---

## 1. 逐环节对比（带个人使用判定）

| # | 环节 | 企业 RAG | kb2 | 个人需要？ |
|---|---|---|---|---|
| 1 | 文档解析 | PDF / Word / HTML / 表格 / 公式 | 只吃 Markdown | **不需要** |
| 2 | 分块 | 语义分块 + 父子块 + 重叠 | **已做**：小节标题 + 30–400 字窗切原子 | 已有，父子块可选 |
| 3 | 元数据 | 时间 / 类型 / 来源 / 权限 / 租户 | `status` / 时间 / 类型 | **scope 与别名需要**，权限租户不需要 |
| 4 | 向量化 | 专用模型 + 批量 + **缓存** | qwen3.7 1024 维 | **需要缓存层**（见第 4 节） |
| 5 | 索引 | 向量库 + 倒排 + 图 | SQLite 倒排 + `.f32` 全量加载 | **不需要外置**（见第 5 节） |
| 6 | **Query 理解** | 改写 / HyDE / 多查询 / step-back | 无 | **只要抽取式**（见第 6 节） |
| 7 | 检索 | 向量 + 关键词 + 元数据过滤 + 图 | BM25 + 向量 + RRF | 机制上够用 |
| 8 | 重排 | 通常必开 | 有，默认关（工程库实测无收益） | 有依据的选择 |
| 9 | 上下文组装 | token 预算 + lost-in-the-middle + 压缩 | **去重已做** | 缺 lost-in-middle 排序（可选） |
| 10 | **最近窗口保底** | 常驻最近 N 轮原文 | **无** | **需要**（第一真差距） |
| 11 | 生成 | LLM + 提示词工程 | 不做（设计如此） | 不需要，交给 MCP 客户端 |
| 12 | 评估 | RAGAS + 人工 | top1/top3 + 断言 | 已有，够用 |
| 13 | 反馈闭环 | badcase 回流 / 点击 / A/B | 无 | **不需要**（单人用，自己记得） |
| 14 | 多租户 | user_id / ACL | 无 | **不需要** |

## 2. 三个「完全没有」的

### 2.1 最近窗口保底 —— 早就有，但实测无效

> **更正（2026-11-20）**：本节原先写「kb2 的适配器只有 search，不拼最近轮次」，
> 这与代码和运行产物都矛盾，是文档漂移。事实如下。

官方 BM25 基线（`sentinel-bm25-recent6`）的结构是「BM25 top-k + 最近 6 轮原文」。
kb2 的聊天适配器**从 2026-11-13 起就实现了同一条通道**：`mykb2.py` 的 `RECENT_TURNS`
读 `MYKB2_RECENT_TURNS`（默认 6），在 `retrieve()` 里把最近 6 轮拼进 prompt 的「【最近的对话】」段。
证据两条：代码（`adapters/mykb2.py:32` 与 `:149`）；运行产物（2026-11-13 的 809 题全量 run
里 807 条 prompt 含该段，2026-11-14 的 M02 run 392/392）。

所以 M01 34.7 / M02 39.2 **是在窗口开着的情况下测出来的**——「少了一条保底通道」
不是这个分数的原因。

实测（2026-11-20，M02 抽样 120 条 / 107 unit，unit 级配对）：

| 对照 | A（窗口 0） | B（窗口 6） | 配对差 | 95% 区间 |
|---|---:|---:|---|---|
| 整体 | 35.68 | 36.63 | +0.9 pp | [−14.0, +12.2] |
| 日常题（35 unit） | — | — | +8.6 pp | — |
| 长期题（72 unit） | — | — | −2.8 pp | — |

代价是 prompt 字符 +60%。**判定：无效**（±2 pp 内）。
更早的 3 轮 vs 6 轮对比（`BENCHMARK.md` §10.3.2）也只在噪声内：34.73/39.19 vs 35.26/38.99。

结论：这条通道**保留默认开**（它不花钱，日常题方向为正），但**不再作为提升手段**。
上一版把「补窗口保底」列为第一刀、并预测「补上至少追平官方基线」，这个预测被本次实测否定。

### 2.3 元数据：scope 与 user_id

Two 件事分开看：

- **user_id 隔离**：PrecisionMemBench 测的「一个库里有多个用户的数据」——对个人使用**不需要**
- **scope 过滤**：belief 自带 `scope: [domain:code]`，kb2 不看这个字段，会把写作域的卡也捞出来。**对个人有用**——工程卡和法律卡混在一个库里时，能按域收窄

## 3. 分块：原子化就是 chunking，我先前写错了

kb2 已有 chunking，而且比多数方案细：

- 按小节标题优先切（`排障/要点/结论/根因/现象/原因` 等）
- 长度窗 30–400 字（更碎则噪声大，更长则语义分散）
- 标题单独成原子（`nature='title'`），单独参与打分

企业方案里多出来的「父子块」（小块检索、大块返回）对**长文档**有用；对卡片式语料，一张卡本身就不长，父子块收益有限。

---

## 4. 缓存层：值得做，是纯收益

| 缓存什么 | 收益 | 风险 | 工作量 |
|---|---|---|---|
| **查询向量**（query → vector） | 省 166ms embedding 往返 + API 费 | 无（同一 query 向量不变） | ~20 行 LRU |
| 检索结果 | 省整个检索 | 索引更新后失效，需版本号 | 中 |
| 向量索引 | 已做（`_vecCache`） | — | 已完成 |

**查询向量缓存是纯赚的**：当前 p50 189ms 里 166ms 是 embedding，重复查询直接省掉九成延迟。个人使用时调试会反复问同一件事，命中率不低。

实现要点：

- key 用 query 文本的 hash（不用 query 向量，否则要先算向量）
- LRU 上限按内存定（1024 维 float32 = 4KB/条，1000 条约 4MB）
- 命中率可以在 `memory_stats` 里暴露，便于观察

---

## 5. 外置向量库：不需要，而且你的质疑对

外置向量库（Milvus / pgvector）解决的问题是 **内存、并发、水平扩展、元数据过滤**。它**不改变检索算法**——还是「算相似度、排序、取 top-k」，只是换了个存储引擎。

对个人使用：当前 5962 条向量 24MB 全量加载，绰绰有余。`vectorTopK` 是纯 JS 循环，1024 维 × 5962 条约 610 万次乘加，实测在 10ms 量级。

只有到万卡级、或需要多进程共享索引时才值得考虑——而那时候「再套一层」的成本（序列化、网络往返、一致性）会超过收益。

## 6. Query 理解：生成式不要，抽取式可以

### 三种方法的机制与风险

| 方法 | 机制 | 对垂直领域的风险 |
|---|---|---|
| **HyDE** | 先生成「假设答案」，再用它检索 | 假设答案会出现原文没有的术语。法学尤其危险——「善意取得」与「善意」在法律语境里不是一回事 |
| **生成式改写** | LLM 重写 query | 改写引入原文没有的概念 → **幻觉被放大到检索层**，且用户看不到改写结果，无法察觉 |
| **step-back** | 抽象成更一般的问题 | 抽象会丢掉具体限定词（「2024 年修订后」这类关键约束） |

**这三条对垂直领域都可能是负收益**，方向性判断与 HyDE 在法学域劣化的经验一致。

### 低风险替代：抽取式改写

不做生成，只做确定性变换：

1. 抽关键词：去掉语气词、代词、疑问词
2. **同义词 / 别名扩展**：`k8s` → `kubernetes`、法律术语别名表

**零幻觉风险**，且直接补上 PrecisionMemBench 里 Alias resolution 3/23 的短板。

代价：同义词表要人维护。法学术语别名表本身就是有价值的知识资产，不算纯成本。

### 结论

| 做不做 | 项目 |
|---|---|
| **做** | 抽取式改写（关键词 + 别名表） |
| **不做** | HyDE、生成式改写、step-back |
| **待验证** | 如果要试生成式改写，必须先用现有 59 条标注做 A/B，确认 top1/top3 不降 |

---

## 7. 上下文组装：去重已做，缺的是排序

已做的：

- **内容级去重**：真实工程库 top5 唯一内容 3.60 → 5.00
- **多卡重叠比对**：做了，但负提升，已否决

缺的（可选）：

- **lost-in-the-middle 排序**：把最相关的放头尾、中等的放中间。依据是长上下文模型对中间内容的注意力衰减。对 top5 这种短上下文收益有限，优先级低

## 8. 三刀的实际结果（2026-11-20 实测后重写）

| 刀 | 状态 | 实测 |
|---|---|---|
| 最近窗口保底 | **早就有，实测无效** | 0 vs 6 轮 +0.9 pp，CI 跨 0；见 §2.1 |
| 查询向量缓存 | **已实现，采纳** | 命中 54 ms，净省 191 ms（CI [165,227]） |
| 抽取式改写 | **已实现，收益过小，默认关** | PrecisionMemBench +1 条题（13.2%→14.5%），噪声内 |

本轮还补了两刀，都不在原清单里：

| 项 | 实测 |
|---|---|
| **检索结果缓存** | 命中 1 ms（对照 55 ms），返回 64/64 一致 |
| **scope 过滤** | PrecisionMemBench 13.2% → 23.7%；与别名叠加 26.3%（+10 条题） |
| **法学正文入索引** | 正文细节 top1 87.7% → 97.6%（+93 条题），概念名 recall 不降 |

完整记录见 [EXPERIMENT-2026-11-20.md](./EXPERIMENT-2026-11-20.md)。

## 9. 不该补的（已验证或不需要）

| 方向 | 原因 |
|---|---|
| 多跳 / 关系扩展 | 桥接精度 1–3%，top3 已 100% 只有下降风险 |
| BM25F 字段加权 | 模拟 +17.5pp，真实实现 −21.7pp |
| 查询级路由 | 59 条上 90% vs 统一 92% |
| 更深的候选池（>80） | 万卡级封顶，边际收益趋零 |
| 重排默认开 | 长文档有增益，工程库无收益且多付 0.8 秒 |
| HyDE / 生成式改写 / step-back | 垂直领域幻觉风险，且不可见 |
| 外置向量库 | 规模未到，套娃成本超过收益 |
| 文档解析 / 多租户 / ACL / 反馈闭环 / RAGAS | 个人使用不需要 |

---

## 10. 一句话总结

**kb2 的检索段可以（工程库 top1 93.2% 到顶）。2026-11-20 复测后修正：所谓「后面缺上下文保底」不成立——最近窗口一直开着，而且开了也没用（+0.9 pp）。真正缺的是「该不该返回」这一层（scope）和「正文有没有进索引」（法学库 385 万字此前完全不可检索）。**

企业 RAG 的优势不在算法，在这两端的工程。而「魔改 Qwen RAG 反而不如」的原因是：只保留了检索段，等于砍掉了它主要的工程价值。

按个人使用补三刀（窗口保底、向量缓存、抽取式改写），其余十条不背。
