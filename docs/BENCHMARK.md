「原子数」随索引版本变动，标注为约数。

### 为什么用人工标注

自动指标（比如用另一个模型判断相关性）会引入第二层误差——你测的是两个模型的组合，还是被测系统？所以这里的目标卡全部由人工指定，一条题对应一张或多张卡。

代价是样本量小（59、40、30 条），所以文中所有「提升 2%」之类的结论都标注了题数，供判断是否在噪声内。

## 2. 指标定义

| 指标 | 定义 |
|---|---|
| **top1** | 目标卡出现在第 1 名的题数 / 总题数 |
| **top3 / top8 / top16** | 目标出现在前 N 名的题数 / 总题数 |
| **命中（hit）** | 目标 evidence 任一条出现在返回结果中的比例 |
| **覆盖（coverage）** | 命中的 evidence 条数 / 应命中的 evidence 总数 |
| **MRR** | 目标排名倒数的均值 |

工程库用 top1/top3；聊天库用命中/覆盖（一条题对应多条 evidence，只看第一名没有意义）。

---

## 3. 核心结果（工程库，59 条标注）

**这是本项目唯一可引用的生产基线。**

| 配置 | top1 | top3 |
|---|---:|---:|
| 纯 BM25 | **93.2%** | **100%** |
| + 向量 RRF | 92% | 100% |
| + 向量 RRF + rerank（修正输入后） | 90% | 98% |

- 向量在工程库上没有收益（top1 反而低 1.2pp，1 条题，噪声内）
- rerank 少 2pp，同样是 1–2 条题
- **所以工程档的默认配置是向量开、rerank 关**——不是因为向量更好，是因为它不更差且能改善别的域

排除 4 条「题目本身有歧义」的样本后，top1 93%（26/28）、top3 100%（28/28）。

## 4. 聊天域（M01 30 题 / M02 40 题）

聊天库的问题性质与工程库完全不同：要想起多轮对话中的细节，一条题往往对应多条 evidence。

| 配置 | 命中 | 覆盖 |
|---|---:|---:|
| BM25 单路（top8） | 45.0% | — |
| 向量单路（top8） | 57.5% | — |
| RRF 融合（top16，pool 20） | 57.5% | — |
| RRF 融合（top16，pool 80） | **65.0%** | **0.588** |

第 16 轮修正前后：

| 指标 | 旧（错误输入） | 修正后 |
|---|---:|---:|
| M02 命中 | 48.3% | 48.3% |
| M02 覆盖 | 0.403 | 0.394 |

修正没有改变聊天域结论，但改变了工程域的结论（73% → 90%）。这件事本身说明：**评测脚本的一个小改动可以让 17pp 的结论反转**。

## 6. 延迟

工程库 571 卡，p50 189 ms / p95 225 ms。

延迟构成（单次检索）：

| 环节 | 耗时 | 占比 |
|---|---:|---:|
| embedding 往返（远端） | 166 ms | 88% |
| RRF 融合 | 33 ms | 17% |
| 向量 topK（本地） | 10 ms | 5% |
| SQL 全表读 | 8 ms | 4% |
| BM25 | 2.8 ms | 1.5% |

**结论：本地检索很便宜，九成延迟来自一次远端 embedding 调用。** 想提速只能缓存查询向量或换本地模型，优化 SQL 没有意义。

这也是 `MEM_VECTOR` 默认在工程库开启的另一个代价——每次查询多 166ms。如果对延迟敏感，关掉向量换 BM25-only，工程库 top1 只差 1 条题。

## 7. 候选池不变量（可证伪的设计断言）

设计断言：**加深候选池只应减少「过滤后名额不足」这类损失，不应改变任何已排序结果。**

验证（第 19 轮，工程库 64 条查询）：pool 5 / 20 / 80 三档的前 5 名**完全一致 64/64**。

这条不变量已经写进 `scripts/selfcheck.mjs`。如果哪天它失败了，说明融合逻辑有状态泄漏——这比任何准确率指标都更早发现问题。

## 8. 冻结说明

`kb2-bench-2.2` 已冻结。冻结的含义：

- 数据集与指标定义不再变动，历史数字可与新数字直接对比
- 冻结后不要再做「换个指标口径重测」这类事——那会让所有历史结论失去可比性
- 新的实验必须用同一份题集与同一套指标

## 10. 与公开基准的关系（必读，防误读）

本项目**没有向任何公开榜提交过成绩**。下面列出可比基准的官方数字，以及自测结果与它们的关系——两者的口径不同，不能直接相减。

### 10.1 chat-memory-benchmark 2.2（陪伴型记忆，封存集抽样）

榜单来自 [Ornn8/chat-memory-benchmark](https://github.com/Ornn8/chat-memory-benchmark)，三榜分数是 A（通过率，成对题按对计），成本 C 另计，综合分 S = A − 3·log2(C/C_ref)。

| 榜 | 系统 | A | S | C(¥) |
|---|---|---:|---:|---:|
| 短对话 M01 | Qwen 基础方案（参照） | 42.5 | 42.5 | 1.121 |
| 短对话 M01 | **BM25 + 最近 6 轮（本地基线）** | 37.4 | 41.9 | 0.398 |
| 短对话 M01 | 全塞（110k 窗口，抽样） | 57.5 | 41.9 | 41.125 |
| 长对话 M02 | Qwen 基础方案（参照） | 47.4 | 47.4 | 4.755 |
| 长对话 M02 | **BM25 + 最近 6 轮（本地基线）** | 45.1 | 49.2 | 1.879 |
| 长对话 M02 | 全塞（抽样） | 24.1 | 14.6 | 42.639 |
| 自然用记忆 | Qwen 基础方案 | 52.5 | 52.5 | 11.481 |
| 自然用记忆 | **BM25 + 最近 6 轮（本地基线）** | 43.4 | 48.3 | 3.716 |

加粗那行是 kb2 最接近的对照：**它用的就是 BM25 + 最近 N 轮，没有向量、没有融合、没有候选池**。

### 10.2 kb2 的自测与它的关系

kb2 在 M01 / M02 上跑的是**自建评测**，指标是「evidence 命中率 / 覆盖率」，不是榜上的 A（通过率）。

| 指标 | 数值 | 口径 |
|---|---:|---|
| M02 evidence 命中（pool 20，旧默认） | 48.3% | 自建：40 题，目标 evidence 是否出现在返回结果 |
| M02 evidence 命中（pool 80） | **65.0%** | 同上，仅改候选池深度 |
| M01 evidence 命中（limit 14） | 53.3% | 自建：30 题 |
| 工程库 top1 / top3 | 93.2% / 100% | 自建：59 题人工标注卡片 |

**能不能和 10.1 的 A 分比？不能。** 理由有三个：

1. **指标不同**：evidence 命中看「检索到的内容里有没有正确的那条」；A 分看「最终回答满足 required、没有撞 forbidden」——中间隔着一整个答题环节。
2. **题不同**：自建题集是抽样自题库，题数与题型分布都与封存集不同。
3. **kb2 没跑答题**：它只负责检索，不负责生成回答。榜单测的是「检索 + 生成」的端到端结果。

可以成立的推断只有一条：**kb2 的检索链路是 BM25 基线的增强版**（多了向量路、RRF、去重、自适应池），而 BM25 基线在 M01/M02 上分别是 37.4 / 45.1。增强能不能换来 A 分的提升，**必须提交榜单才知道**。

### 10.3 chat-memory-benchmark 1.0（六人物 714 题）

1.0 已不是主榜，kb2 同样未提交。榜单区间的参考（同一题库、不同系统、完整卷）：

| 系统 | 通过 / 已答 |
|---|---:|
| OpenViking（火山引擎） | 555 / 714 |
| dsh-neo4j-memory（作者自测，未复核） | 684 / 714 |
| Qwen RAG（评测方搭建的对照） | 596 / 714 |
| dsh-memory-brain | 583 / 714 |
| SeekMemory | 230 / 714 |
| 无记忆（参照） | 见 2.2 的 1.1–28.0 区间 |

这组数字说明一件事：**这批题的天花板不在检索层**。最强与最弱差了 3 倍，而它们大多用的是差不多的关键词检索——差距来自「记忆怎么组织、什么时候提」，不是「分数排得准不准」。

### 10.4 本次实测的「坏消息」，也写在这里

- **聊天域是弱项**：M02 evidence 命中 48.3%（pool 20），即使调到 pool 80 也只到 65%。对照榜单，BM25 基线的 A 分是 45.1——kb2 在聊天域没有拉开差距的证据。
- **只在两个合成人物上测过**：M01/M02 是题库作者构造的两个人物，样本有限，结论不能外推到真实用户的聊天史。
- **工程库的高分不可迁移**：93.2% 来自短标题 + 完整正文的结构（原子/卡 9.4、标题 34.7 字），换成聊天库（原子/卡 2.0）就掉到 48.3%。同一套参数不可能同时服务两种语料——这就是三档 Profile 存在的原因。
- **没有真实用户数据**：所有数字都来自构造语料与人工标注，没有线上 A/B。
