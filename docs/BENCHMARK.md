# Benchmark

所有数字来自本项目的实测脚本与人工标注题集，不是估计值。实验过程见 [DEBUG-LOG.md](./DEBUG-LOG.md)。

---

## 1. 数据集

| 库 | 卡片 | 原子 | 题目 | 标注方式 |
|---|---:|---:|---:|---|
| 工程库 | 571 | 5 400± | 59 条 | 人工标注目标卡，7 个目录 |
| 聊天库（M01） | 5 413 | — | 30 条 | 人工标注 evidence |
| 聊天库（M02） | 5 413 | — | 40 条 | 人工标注 evidence |
| 法学 wiki | 941 | 8 468 | 自带 bench | MRR |

「原子数」随索引版本变动，标注为约数。

### 为什么用人工标注

自动指标（比如用另一个模型判断相关性）会引入第二层误差——你测的是两个模型的组合，还是被测系统？所以这里的目标卡全部由人工指定，一条题对应一张或多张卡。

代价是样本量小（59、40、30 条），所以文中所有「提升 2%」之类的结论都标注了题数，供判断是否在噪声内。

## 2. 指标定义

| 指标 | 定义 |
|---|---|
| **top1** | 目标卡出现在第 1 名的题数 / 总题数 |
| **top3 / top8 / top16** | 目标出现在前 N 名的题数 / 总题数 |
| **命中（hit）** | 目标 evidence 任一条出现在返回结果中的比例 |
| **覆盖（coverage）** | 命中的 evidence 条数 / 应命中的 evidence 总数 |
| **MRR** | 目标排名倒数的均值 |

工程库用 top1/top3；聊天库用命中/覆盖（一条题对应多条 evidence，只看第一名没有意义）。

---

## 3. 核心结果（工程库，59 条标注）

**这是本项目唯一可引用的生产基线。**

| 配置 | top1 | top3 |
|---|---:|---:|
| 纯 BM25 | **93.2%** | **100%** |
| + 向量 RRF | 92% | 100% |
| + 向量 RRF + rerank（修正输入后） | 90% | 98% |

- 向量在工程库上没有收益（top1 反而低 1.2pp，1 条题，噪声内）
- rerank 少 2pp，同样是 1–2 条题
- **所以工程档的默认配置是向量开、rerank 关**——不是因为向量更好，是因为它不更差且能改善别的域

排除 4 条「题目本身有歧义」的样本后，top1 93%（26/28）、top3 100%（28/28）。

## 4. 聊天域（M01 30 题 / M02 40 题）

聊天库的问题性质与工程库完全不同：要想起多轮对话中的细节，一条题往往对应多条 evidence。

| 配置 | 命中 | 覆盖 |
|---|---:|---:|
| BM25 单路（top8） | 45.0% | — |
| 向量单路（top8） | 57.5% | — |
| RRF 融合（top16，pool 20） | 57.5% | — |
| RRF 融合（top16，pool 80） | **65.0%** | **0.588** |

第 16 轮修正前后：

| 指标 | 旧（错误输入） | 修正后 |
|---|---:|---:|
| M02 命中 | 48.3% | 48.3% |
| M02 覆盖 | 0.403 | 0.394 |

修正没有改变聊天域结论，但改变了工程域的结论（73% → 90%）。这件事本身说明：**评测脚本的一个小改动可以让 17pp 的结论反转**。

## 5. 法学 wiki（941 卡）

| 检索路 | 结果 |
|---|---|
| BM25 | MRR 0.529 |
| dense（向量） | 0.434 |
| 概念名 recall@1 | 98.9%（940 张卡） |

密集向量在这个库上是负收益（0.434 < 0.529），所以 wiki 档默认关向量。原因见 [TUNING.md](./TUNING.md#mem_vector--向量开关)：卡片是概念名驱动的，标题即答案。

## 6. 延迟

工程库 571 卡，p50 189 ms / p95 225 ms。

延迟构成（单次检索）：

| 环节 | 耗时 | 占比 |
|---|---:|---:|
| embedding 往返（远端） | 166 ms | 88% |
| RRF 融合 | 33 ms | 17% |
| 向量 topK（本地） | 10 ms | 5% |
| SQL 全表读 | 8 ms | 4% |
| BM25 | 2.8 ms | 1.5% |

**结论：本地检索很便宜，九成延迟来自一次远端 embedding 调用。** 想提速只能缓存查询向量或换本地模型，优化 SQL 没有意义。

这也是 `MEM_VECTOR` 默认在工程库开启的另一个代价——每次查询多 166ms。如果对延迟敏感，关掉向量换 BM25-only，工程库 top1 只差 1 条题。

## 7. 候选池不变量（可证伪的设计断言）

设计断言：**加深候选池只应减少「过滤后名额不足」这类损失，不应改变任何已排序结果。**

验证（第 19 轮，工程库 64 条查询）：pool 5 / 20 / 80 三档的前 5 名**完全一致 64/64**。

这条不变量已经写进 `scripts/selfcheck.mjs`。如果哪天它失败了，说明融合逻辑有状态泄漏——这比任何准确率指标都更早发现问题。

## 8. 冻结说明

`kb2-bench-2.2` 已冻结。冻结的含义：

- 数据集与指标定义不再变动，历史数字可与新数字直接对比
- 冻结后不要再做「换个指标口径重测」这类事——那会让所有历史结论失去可比性
- 新的实验必须用同一份题集与同一套指标

## 9. 复现

```bash
# 建索引
MEM_VAULT=/path/to/vault node src/index.mjs

# 自检（只读，可指向生产库）
node scripts/selfcheck.mjs --vault /path/to/vault

# 完整检查（含服务层 MCP 往返，只能指向副本）
node scripts/selfcheck.mjs --vault /tmp/probe-vault --serve
```

自检输出：索引完整性、归档卡规模、候选池不变量、延迟构成、服务层 top1/top3。退出码 0 全通过 / 1 有 FAIL / 2 有 WARN。

工程库基线（2026-11-14，571 卡）：**top1 93.2% / top3 100%（59 条有效题）**，p50 189 ms、p95 225 ms。
