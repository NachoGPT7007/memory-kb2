「原子数」随索引版本变动，标注为约数。

### 为什么用人工标注

自动指标（比如用另一个模型判断相关性）会引入第二层误差——你测的是两个模型的组合，还是被测系统？所以这里的目标卡全部由人工指定，一条题对应一张或多张卡。

代价是样本量小（59、40、30 条），所以文中所有「提升 2%」之类的结论都标注了题数，供判断是否在噪声内。

## 2. 指标定义

| 指标 | 定义 |
|---|---|
| **top1** | 目标卡出现在第 1 名的题数 / 总题数 |
| **top3 / top8 / top16** | 目标出现在前 N 名的题数 / 总题数 |
| **命中（hit）** | 目标 evidence 任一条出现在返回结果中的比例 |
| **覆盖（coverage）** | 命中的 evidence 条数 / 应命中的 evidence 总数 |
| **MRR** | 目标排名倒数的均值 |

工程库用 top1/top3；聊天库用命中/覆盖（一条题对应多条 evidence，只看第一名没有意义）。

---

## 3. 核心结果（工程库，59 条标注）

**这是本项目唯一可引用的生产基线。**

| 配置 | top1 | top3 |
|---|---:|---:|
| 纯 BM25 | **93.2%** | **100%** |
| + 向量 RRF | 92% | 100% |
| + 向量 RRF + rerank（修正输入后） | 90% | 98% |

- **向量在工程库上的收益体现在 top3，不在 top1**：BM25 ×3.0 是 top3 98%，hybrid 是 100%；top1 两者都是 92%
- 早期用 leave-one-out 得到「加入向量一位未变」，那是天花板效应——该方法用卡正文当查询，BM25 已 40/40 满分，向量无处发力（2026-11-20 复测）
- rerank 少 2pp，是 1–2 条题，在噪声内
- **所以工程档的默认配置是向量开、rerank 关**——向量的价值在 top3 与跨域一致性，不在 top1

排除 4 条「题目本身有歧义」的样本后，top1 93%（26/28）、top3 100%（28/28）。

## 6. 延迟

工程库 571 卡，p50 189 ms / p95 225 ms。

延迟构成（单次检索）：

| 环节 | 耗时 | 占比 |
|---|---:|---:|
| embedding 往返（远端） | 166 ms | 88% |
| RRF 融合 | 33 ms | 17% |
| 向量 topK（本地） | 10 ms | 5% |
| SQL 全表读 | 8 ms | 4% |
| BM25 | 2.8 ms | 1.5% |

**结论：本地检索很便宜，九成延迟来自一次远端 embedding 调用。** 想提速只能缓存查询向量或换本地模型，优化 SQL 没有意义。

这也是 `MEM_VECTOR` 默认在工程库开启的另一个代价——每次查询多 166ms。如果对延迟敏感，关掉向量换 BM25-only，工程库 top1 只差 1 条题。

## 7. 候选池不变量（可证伪的设计断言）

设计断言：**加深候选池只应减少「过滤后名额不足」这类损失，不应改变任何已排序结果。**

验证（第 19 轮，工程库 64 条查询）：pool 5 / 20 / 80 三档的前 5 名**完全一致 64/64**。

这条不变量已经写进 `scripts/selfcheck.mjs`。如果哪天它失败了，说明融合逻辑有状态泄漏——这比任何准确率指标都更早发现问题。

## 10. 与公开基准的关系（必读，防误读）

本项目**没有向任何公开榜提交过成绩**。下面列出可比基准的官方数字，以及自测结果与它们的关系——两者的口径不同，不能直接相减。

### 10.1 chat-memory-benchmark 2.2（陪伴型记忆，封存集抽样）

榜单来自 [Ornn8/chat-memory-benchmark](https://github.com/Ornn8/chat-memory-benchmark)，三榜分数是 A（通过率，成对题按对计），成本 C 另计，综合分 S = A − 3·log2(C/C_ref)。

| 榜 | 系统 | A | S | C(¥) |
|---|---|---:|---:|---:|
| 短对话 M01 | Qwen 基础方案（参照） | 42.5 | 42.5 | 1.121 |
| 短对话 M01 | **BM25 + 最近 6 轮（本地基线）** | 37.4 | 41.9 | 0.398 |
| 短对话 M01 | 全塞（110k 窗口，抽样） | 57.5 | 41.9 | 41.125 |
| 长对话 M02 | Qwen 基础方案（参照） | 47.4 | 47.4 | 4.755 |
| 长对话 M02 | **BM25 + 最近 6 轮（本地基线）** | 45.1 | 49.2 | 1.879 |
| 长对话 M02 | 全塞（抽样） | 24.1 | 14.6 | 42.639 |
| 自然用记忆 | Qwen 基础方案 | 52.5 | 52.5 | 11.481 |
| 自然用记忆 | **BM25 + 最近 6 轮（本地基线）** | 43.4 | 48.3 | 3.716 |

加粗那行是 kb2 最接近的对照：**它用的就是 BM25 + 最近 N 轮，没有向量、没有融合、没有候选池**。

### 10.2 kb2 的自测与它的关系

kb2 在 M01 / M02 上跑的是**自建评测**，指标是「evidence 命中率 / 覆盖率」，不是榜上的 A（通过率）。

| 指标 | 数值 | 口径 |
|---|---:|---|
| M02 evidence 命中（pool 20，旧默认） | 48.3% | 自建：40 题，目标 evidence 是否出现在返回结果 |
| M02 evidence 命中（pool 80） | **65.0%** | 同上，仅改候选池深度 |
| M01 evidence 命中（limit 14） | 53.3% | 自建：30 题 |
| 工程库 top1 / top3 | 93.2% / 100% | 自建：59 题人工标注卡片 |

**能不能和 10.1 的 A 分比？不能。** 理由有三个：

1. **指标不同**：evidence 命中看「检索到的内容里有没有正确的那条」；A 分看「最终回答满足 required、没有撞 forbidden」——中间隔着一整个答题环节。
2. **题不同**：自建题集是抽样自题库，题数与题型分布都与封存集不同。
3. **kb2 没跑答题**：它只负责检索，不负责生成回答。榜单测的是「检索 + 生成」的端到端结果。

可以成立的推断只有一条：**kb2 的检索链路是 BM25 基线的增强版**（多了向量路、RRF、去重、自适应池），而 BM25 基线在 M01/M02 上分别是 37.4 / 45.1。增强能不能换来 A 分的提升，**必须提交榜单才知道**。

### 10.3 chat-memory-benchmark 1.0：本地口径 654 / 714

1.0 已不是主榜。kb2 在**本地**跑过完整卷，用的是自建接入与判分（`exp.mjs` / `run.mjs` / `judge.mjs`），**未向官方提交复核**：

| 系统 | 成绩 | 口径 |
|---|---:|---|

### 10.3.1 同一个系统，1.0 到 2.2 为什么掉下来

2026-11-13 的会话记录了这个落差的全过程。1.0 的 654 与 2.2 的 A 分之间隔着三件事：

| 差异 | 1.0 | 2.2 |
|---|---|---|
| 计分 | 自研判分（整卷通过率） | 官方 rubric + 成对计分 + 日常/长期分开 |
| 历史密度 | 六人物 714 题 | 两个人物、半年聊天史、每题需多条 evidence |
| 接入形态 | 自建 runner，短期窗口 6 轮 / 每条 300 字 | 官方 harness，适配器参数一度偏离 |

对齐窗口参数（3 轮 → 6 轮、截断 420 → 300 字）后重跑，两个口径的变化在 ±1.2 分以内，而 95% 区间是 ±6～7 分——**在噪声里，不是原因**。

### 10.4 本次实测的「坏消息」，也写在这里

- **聊天域是弱项**：M02 evidence 命中 48.3%（pool 20），即使调到 pool 80 也只到 65%。对照榜单，BM25 基线的 A 分是 45.1——kb2 在聊天域没有拉开差距的证据。

## 11. PrecisionMemBench：检索精度实测 13.2%

[PrecisionMemBench](https://github.com/tenurehq/precisionmembench) 是**唯一的纯检索**记忆基准：不生成答案、不判分，只断言「每个 case 必须返回哪些记忆、必须不返回哪些」。噪声是硬失败。

数据：35 个 belief（含别名、替代链、跨用户隔离样本）、77 个 case、13 类。`shouldOnlyInclude: []` 的 32 个 case 表示**只应返回空**——返回任何 belief 都算失败。

接入方式：把 belief 建成卡（`_id` 作文件名便于映射），用 kb2 检索 top10，按断言判分。脚本：[`bench/eval-precision.mjs`](../bench/eval-precision.mjs)。

### 结果

**10 / 76 = 13.2%**

### 11.1 两项改动的实测（2026-11-20，服务层口径）

评测脚本已改为走真实 MCP stdio 往返（原版直接 import 索引层，测不到服务层改动）：

| 配置 | 通过 | 说明 |
|---|---:|---|
| 基线 | 10/76 = 13.2% | BM25 路，limit 10 |
| + 抽取式改写 | 11/76 = 14.5% | Alias 2/23 → 3/23，只救「纯别名词短查询」；默认关 |
| + scope 收窄 | 18/76 = 23.7% | Scope 0/12 → 3/12，8 条变好 0 条变差 |
| + 两者叠加 | **20/76 = 26.3%** | 叠加优于单独，说明作用在不同 case 上 |

**scope 的边界**：实验里 query 的 scope 由评测方直接给出；生产里要靠调用方显式传
（`memory_search(scope: ["domain:code"])`），或者做一轮 cwd + 词表的自动推断——后者没做。

**这个数字要与官方基线一起看**（同一基准、封存集、各系统官方提交）：

| 系统 | 通过率 | active retrieval 通过 |
|---|---:|---:|
| Qwen3（向量） | 14.3% | 1 / 77 |
| Nomic（向量） | 14.3% | 1 / 77 |
| **Hindsight（商业）** | 14.3% | 0 / 77 |
| **Mem0（商业）** | 11.7% | 0 / 77 |
| Cognee | 11.7% | 0 / 77 |
| **memory-kb2** | **13.2%** | 见下 |

**这个基准对几乎所有系统都是 12–14%。** 原因不是系统都差，是断言极严：32 个 case 要求「返回空」，而任何检索系统默认都会返回 top-k。

### 分类明细

| 分类 | 通过 |
|---|---:|
| Alias resolution | 2/23 |
| Scope disambiguation | 0/12 |
| Fuzzy matching | 3/7 |
| Type routing | 0/6 |
| Design boundary | 2/6 |
| Budget eviction | 1/5 |
| Relation expansion | 0/4 |
| Supersession chain | 0/3 |
| Ranking stability | 0/2 |
| Counter-signal | 0/2 |
| Cross-user isolation | 0/1 |

### 这 13.2% 说明什么

**kb2 与官方基线持平，但没有超过它们。** 三个具体短板：

1. **没有 scope 过滤**——belief 自带 `scope: [domain:code]`，kb2 不看这个字段，把写作域的卡也捞出来
2. **没有 user_id 隔离**——数据里有跨用户泄露样本，kb2 的卡没有用户维度
3. **别名解析弱**——`k8s`/`kube` → `kubernetes` 靠字符重叠，而二元组分词为中文设计

前两条是数据结构缺口，第三条是分词策略边界。

### 判分口径的重要说明（曾出错一次）

初版判分把 `shouldOnlyInclude: []` 当作「无断言」跳过了，得出 **44.7%**。那 32 个 case 因此变成白送分。修正后是 **13.2%**。

这个错误值得记下来：**「空断言」不等于「没有断言」，它是最强的那条断言**——要求你什么都不返回。

### 与另外两个基准的关系

| 基准 | 测什么 | kb2 结果 | 口径 |
|---|---|---|---|
| PrecisionMemBench | **纯检索精度**（断言式） | 10/76 = 13.2% | 检索输出，不含生成；官方基线同为 12–14% |
| chat-memory-benchmark 2.2 | 端到端（检索 + 答题 + 判分） | M01 ≈35 / M02 ≈39 | 全程接入，官方 harness |
| 自建工程库标注 | 精确找卡 | top1 93.2% / top3 100% | 59 条，短标题语料 |

三个数字不能互相换算。13.2% 的绝对值低，但它与所有公开基线持平——**这个基准衡量的是「克制」，不是「找得到」**：能返回相关记忆很容易，知道什么时候不该返回很难。
