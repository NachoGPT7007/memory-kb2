## 0. 本轮做到哪一步

**只加字段，不自动失活。** 这是本轮明确选择的策略，不是没做完：

- `fact_key` 从提示词 → 解析 → frontmatter → 索引列，全链路打通
- 检索行为**零变化**（`active` 过滤本来就已存在，`fact_key` 不参与检索）
- 替换逻辑（写新值时把旧原子 `active=false`）**未实现**

### 为什么不顺手做替换

LMC-5 的槽位替换成立，是因为它的存储归自己管。在 kb2 里做自动替换意味着：**写一张新卡会去改写其他卡的文件**。误判一次（模型给两条不相干判断用了同一个键）就会静默弃用一条正确结论，而检索侧只会表现为「少了一条」，没有任何报错。

先把字段加进去、观察模型输出质量，是更划算的顺序：如果模型给出的 `fact_key` 粒度混乱，替换逻辑做了也是把噪声放大。

### 两个不起眼但会无声出错的地方

1. **解析正则不认下划线**：原正则 `^ {4}([a-zA-Z]+):` 对 `fact_key` 直接不匹配，字段会静默丢失。索引层「读到了但没报错」是最难查的一类。
2. **`yamlString` 给含冒号的值加引号**：`port:memory-kb2-mcp` 落盘是 `fact_key: "port:memory-kb2-mcp"`。索引侧解析会去引号，所以功能正常——但测试断言若不加引号就会误报失败（本轮踩了一次，已改）。

## 2. 提示词里的规则

```
- fact_key（可选，只给「会被后来者替换」的判断）：这条判断占的是哪个事实槽位。
  同一槽位以后换值时，必须用完全相同的键，否则替换机制认不出来。
  写法：小写英文或数字，用冒号分层，如 port:memory-kb2-mcp、path:vault、model:embed、version:node。
  不加的情况：一次性的观察、踩坑教训、流程步骤、经验总结——这些不会被「替换」，加了反而是噪声。
```

故意允许留空：如果强制每条原子都要 `fact_key`，模型会给经验教训也编一个键，那是把噪声变成结构化的噪声。

### 生产库的真实重建

改 `SCHEMA_ID` 后对生产库跑 `sync()`，**写入设置校验自己抓到了这次变更**：

```
[sync] 写入设置与索引不一致（schema: cards/atoms/postings/v1 → cards/atoms/postings/v2）→ 索引必须重建
耗时 1092 ms，{"added":528,...,"fullBuild":true,"rebuiltReason":"write-settings: schema: ..."}
```

重建后 `atoms` 列含 `fact_key`，`meta.write_settings.schema` = v2，`fact_key` 非空原子 0 条（历史卡没有该字段，符合预期）。

这是第一批 #1 的机制第一次在真实变更上生效——上一轮它只跑了「老库回填」路径。

## 4. 观察什么

接下来几天看两件事：

1. **覆盖率**：新沉淀的卡里有多少原子带 `fact_key`。太高说明模型在硬凑，太低说明提示词没被理解。
2. **键的稳定性**：同一槽位（如 `port:memory-kb2-mcp`）在多次沉淀中是否总用同一个键。键不稳定，替换逻辑就永远无法落地。

查询：

```sql
SELECT fact_key, COUNT(*) FROM atoms WHERE fact_key IS NOT NULL GROUP BY fact_key ORDER BY 2 DESC;
```
